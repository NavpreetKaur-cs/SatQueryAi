# SatQuery AI — Backend

FastAPI backend for SatQuery AI: image upload, and a `/query` endpoint that
routes to the agent (Person 5's module, once it exists) or a keyword-based
mock in the meantime. Tested end to end — upload, single-image query,
before/after compare query, TIFF preview generation, error handling, and
CORS have all been exercised manually while building this.

## Setup

```bash
cd backend
python -m venv .venv

# activate it:
source .venv/bin/activate        # macOS/Linux
.venv\Scripts\activate           # Windows

pip install -r ../requirements.txt
```

If a root `requirements.txt` already exists in the repo with other team
members' packages in it, **merge** the backend block from this one into it
instead of overwriting — see the comment at the top of that file.

## Running it

```bash
cd backend
PYTHONPATH=.. uvicorn main:app --reload --port 8000
```

Check it's alive:
```bash
curl http://127.0.0.1:8000/health
# {"status":"ok","using_real_agent":false}
```

`using_real_agent: false` means it's currently using the mock agent (see
below) — that flips to `true` automatically once Person 5's module exists.

Interactive API docs (auto-generated by FastAPI) are at
`http://127.0.0.1:8000/docs` — useful for testing endpoints by hand.

## Connecting the frontend to this

In `frontend/.env`, set:
```
VITE_API_BASE_URL=http://127.0.0.1:8000
```
The frontend's `src/api/client.js` will then call this backend instead of
its own in-browser mock. No other frontend changes needed.

## Endpoints

### `POST /images`
Multipart file upload. Returns an `imageId` you can reference in `/query`
instead of resending the whole image every time.

```
curl -F "file=@scene.png" http://127.0.0.1:8000/images
```
```json
{
  "success": true,
  "imageId": "d99584d...",
  "width": 400,
  "height": 300,
  "format": "PNG",
  "previewUrl": "/uploads/originals/d99584d....png"
}
```

### `POST /query`
Accepts the team's shared I/O contract shape. Each image can be given
either as `{"imageId": "..."}` (from a prior `/images` upload) or
`{"dataUrl": "data:image/png;base64,..."}` (what the current frontend
sends inline — both are supported).

```json
{
  "images": {
    "before": { "imageId": "d99584d..." },
    "after": null
  },
  "query": "How many built-up structures are visible in this scene?",
  "metadata": {}
}
```

Returns (per the team contract):
```json
{
  "success": true,
  "result": "Detected 4 distinct built-up structures in the selected region.",
  "confidence": 0.88,
  "visual_output": { "regions": [ { "id", "label", "bbox": [x,y,w,h], "score", "image": null } ] },
  "metadata": { "queryType": "count", "modelsUsed": ["mock-agent-v0"] },
  "error": null
}
```

On failure (bad imageId, corrupt image, anything else), `success` is
`false` and `error` has a message — always HTTP 200, so the frontend never
has to special-case a raw 500 vs. a handled failure.

## Integration with the agent

**Confirmed and tested** against the real `agent/controller.py`,
`agent/request.py`, and `agent/response.py` — `using_real_agent` on
`/health` will read `true` automatically once `agent/` exists in your repo
and is importable, no code changes needed. The actual interface is:

```python
from agent.controller import process
from agent.request import AgentRequest, ImageInput

result = process(AgentRequest(query=..., images=[ImageInput(path=...), ...], metadata=...))
result.to_dict()  # {success, answer, task, confidence, model, visual_output, trace, error, metadata}
```

Note this is **not** the `handle_query(query, images, metadata)` shape
mentioned in earlier drafts of this README — that was a guess made before
the real agent code existed, and it turned out to be wrong (images are a
list, not a `{before, after}` dict; field names differ). `agent_client.py`
has been rewritten and tested against the real interface, including the
success/failure and error-propagation paths.

**Still unconfirmed:** the exact shape of `visual_output` coming out of
`modules/single_image`, `modules/change_analysis`, and `modules/multimodal`
(Person 1–4's code), since that depends on what `agent/executor.py`
actually returns from those modules — not something this backend has
been tested against yet. `agent_client._normalize_visual_output()` handles
this defensively (passes through anything that looks like our region-list
shape, doesn't crash on anything else), but don't treat that as confirmed
until you've run a real query through the real modules and checked the
output.

## Known gaps / next steps

- **Image metadata storage is in-memory** (`image_store._REGISTRY`) — it
  resets on every server restart. Fine for a demo, not for anything that
  needs to survive a restart. Swap for SQLite or a JSON sidecar if that
  becomes a problem.
- **GeoTIFF support is partial.** Plain PNG/JPEG and simple single-band
  TIFF work via Pillow. True multi-band GeoTIFF (with CRS/geo metadata)
  needs `rasterio`, which is intentionally NOT in the base
  `requirements.txt` (it pulls in GDAL, a heavy dependency) — install it
  yourself (`pip install rasterio`) and uncomment it in `requirements.txt`
  if your data needs it, and tell the team per rule 8. If `rasterio` isn't
  installed, GeoTIFFs that Pillow can't read will return a clear error
  telling you to install it, rather than failing silently.
- **No auth** — anyone who can reach this server can upload images and run
  queries. Fine for a hackathon demo network; add auth before any real
  deployment.
- **No persistence for query history** — each `/query` call is stateless;
  nothing is logged or stored beyond the uploaded images themselves.
- **Execution summary is minimal** — `metadata.modelsUsed` is the start of
  what the frontend needs to display an "execution summary" (per the
  Person 6 role doc), but it's just a list of one string from the mock
  right now. Once the real agent exists with real model names and timing,
  flesh this out together with the frontend's display of it.
